# Part A - the simulator as it is today (do not regress)

## Purpose
A generic GUI front end for QSPICE circuit models: pick a model, edit component / system / simulation parameters, choose the nodes to show, run QSPICE headless, look at the waveforms, save the image, run again, and compare runs against a held reference. Models are plug-ins; the app contains no circuit knowledge.

## Start and files
- `python Qspice/Simulator/run_simulator.py [--model ID] [--qspice PATH] [--models FOLDER]` (also `python -m qspice_sim` from `Qspice/Simulator`). QSPICE is found via `--qspice`, the Model tab, `QSPICE_EXE`, or `C:\Program Files\QSPICE\QSPICE64.exe`. Models are discovered in `Qspice/*/`, in `--models` folders and in `QSPICE_MODEL_PATH`.
- Code layout: `qspice_sim/` = `model_loader.py` (discovery, manifest validation, adapter loading), `runner.py` (prepare, estimate, run with progress and cancel), `netlist_tools.py` (`.save` replacement, node discovery, `.tran` parsing), `qraw.py` (binary `.qraw`, memory-mapped float64 columns), `decimate.py` (min/max envelope), `config_utils.py` (dotted paths, engineering-notation parser), `gui/` = `main_window.py`, `param_form.py` (schema forms + table editor), `plot_panel.py`, `worker.py`. Tests in `tests/` (`test_core.py`, `test_gui.py` headless with `QT_QPA_PLATFORM=offscreen`, `test_model_7953.py`, `test_sine_force.py`). Run files go to `Qspice/Simulator/runs/<model>/` (git-ignored).

## Model plug-in contract (a folder below `Qspice/`)
- `simulator_model.json` (manifest): `name`, `description`, `config`, `adapter`, parameter forms `components` / `system` / `simulation` (groups of items `{path, label, unit, type float|int|bool|choice|intlist, tip, nullable}`), `tables` (editable lists of dicts with `path`, `title`, `columns`, `new_row`, `add_label`), `plot_groups`, `nodes` (`name`, `label`, `group`, `default`), optional `sample_marker {node, label}`.
- `config.json`: the default configuration (nested JSON, dotted paths address values) plus optional `scenarios` (presets with `overrides`).
- `simulator_adapter.py`: `build(cfg) -> {netlist, t_stop, samples:[{t, label}], warnings}` (raise `ValueError` with a readable message for bad parameters) and optional `summary(cfg) -> [(name, text)]` for the "Derived values" box. Every manifest `path` must exist in the default config; problems are listed on the Model tab.
- The app replaces every `.save` of the netlist by `V(node)` for the ticked nodes only (keeps long runs small); nodes found in the netlist but not in the manifest appear under "Other nodes". Only node voltages and transient analysis are supported.

## Screens and behaviour
- **Toolbar:** model combo, Run (F5), Stop (Esc), Save image (PNG/SVG), Export data (CSV of the visible range), Hold as reference / Clear reference, Load / Save settings (JSON with every parameter and the display options).
- **Model tab:** model choice and description, QSPICE path, add model folder, reset all parameters, reload model files.
- **Components / System tabs:** schema-generated forms with a filter box. Typed values apply on Enter, on leaving the field and when Run / Hold as reference / Save settings / Update estimate is pressed; engineering notation (`1e10`, `470k`, `1.5n`, `2meg`); changed values are highlighted (dark text on yellow, readable in dark themes) with a per-field reset. The System tab has a "Derived values" box from `summary(cfg)`.
- **Simulation tab:** preset scenarios, the input profile as two editable tables (force **pulses**: sensor, start, rise, hold, fall, amplitude, button "Add pulse"; **sine waves**: sensor, start, frequency, cycles, amplitude, button "Add sin"; rows on the same sensor add up), measurement time (run duration or number of scan cycles), solver step, "Update estimate" (points, run time, result size; Run warns above 90 s or 500 MB).
- **Visualization tab:** node tree grouped by plot panel, layout (stacked per group / one plot per node / single overlay), time window, line width, sample markers (`sample_marker`), reference overlay, title annotation listing the changed parameters.
- **Plot:** pyqtgraph, zoom/drag with min/max re-decimation so spikes survive tens of millions of points; replots instantly when the node selection changes and the nodes were saved.
- **Reference workflow:** Hold as reference keeps one run; later runs with other settings are compared against it as dashed traces; replacing the reference asks first; the title shows the changed parameters.
- **Models today:** `TestBoard_ADC124` (one TMUX1308A bank + OPA365 + R/C filter, 3.3 V, VMID 1.65 V, sample node `ain`) and `TestBoard_7953` (one ADS7953 channel mux + OPA365 + sample/hold, VREF 2.5 V, VMID 1.25 V, sample node `sh`, frame timing with `n_adc` / `other_adc_channels`, `repeat`, VMID between channels). Sensors are per-address (`sensor_defaults` + `sensor_overrides`), capacitance `Cp = eps0 * eps33_r * W * L / t` computed in each model's `build_model.sensor_params`, charge source `Bq = d33 * ddt(V(f<k>))`, force nodes `f<k>` carry the applied force in N (1 V = 1 N).
- Known limitations (keep them in the README): one transient run at a time; only saved node voltages are plotted, model-specific post-processing stays in the model scripts; the time estimate is a rough rule.

## Regression baseline
All 56 existing tests keep passing. New features must not change any existing result: with every new setting at its default the netlists and traces of both models are identical to today's (add a test that compares netlist text before/after for both default configs).

## B1. PZT sensor: capacitance override
**Requirement.** The sensor component gets a capacitance value. If a value is entered it replaces the capacitance computed from the size and material; if the field is empty, the capacitance is calculated from the other parameters, as today.
- Config: `sensor_defaults.cp_pF` (default `null`) and the same key allowed in `sensor_overrides[<address>]` (per-sensor). Manifest item `{"path": "sensor_defaults.cp_pF", "label": "Capacitance (override)", "unit": "pF", "type": "float", "nullable": true}` with a tooltip "empty = calculated from size, thickness and eps33" (the form already supports `nullable`; check that an empty field really stores `null` and that reset restores it).
- Both models' `sensor_params()` return `cp = cp_pF * 1e-12` when set (> 0; reject <= 0 with a readable `ValueError`), else the formula. Everything that derives from Cp follows automatically: the `Cp<k>` element, the optional parallel-R loss (`tan_delta`), the open-circuit warnings, the "Derived values" lines (show "Sensor capacitance (sensor 0): 60.7 pF (calculated)" or "(override)"), and the force calculator defaults (B5).
- Show the calculated value as a hint next to the override field (for example "calculated: 60.7 pF") so the user can see what is being overridden.
- Tests: override replaces the netlist `Cp` value; empty restores it; per-address override affects only that sensor; invalid value rejected; Derived values text.

## B2. ADC-Out node (quantised ADC result)
**Requirement.** A new node, "ADC-Out", shows the value the ADC would actually report: the ADC input value at each conversion is converted to a code according to the ADC bit length, rounded, and converted back to a voltage.
- It is a **derived node** computed in Python after the run from the model's `sample_marker` node (`sh` for 7953, `ain` for ADC124) at the adapter's sample times; it is not a QSPICE node and needs no re-simulation. Add a generic mechanism for derived nodes in the app (list them in the node tree and plot groups like real nodes; when a derived node is ticked, automatically add its source nodes to the `.save` list in `_nodes_to_save`).
- Manifest block (new, optional): `"adc_out": {"node": "<source node>", "bits_path": "adc.bits", "vref_path": "...", "vmid_path": "circuit.vmid_v", "label": "ADC-Out (quantised)", "group": "adc"}`. 7953: `circuit.vref_v` (2.5 V); ADC124: its reference is VA = `circuit.vdd_v` (3.3 V). Add `adc.bits` (int, default 12) to both configs and the manifest (ADC group of Components); the ADC124 config has no `adc` section yet, create one.
- Conversion (per sample): `lsb = (vref - v_low) / 2**bits`; `code = clip(round((v_in - v_low) / lsb), 0, 2**bits - 1)`; `v_out = v_low + code * lsb`; `v_low` follows B4. Rounding is round-to-nearest. Samples outside the range are clipped and counted ("N samples clipped" in the status bar and in the table).
- **One ADC-Out trace per chosen channel** (confirmed): the node tree lists "ADC-Out ch<k>" for every sensor channel of the model (15 for TestBoard_7953, 7 for TestBoard_ADC124) and the user ticks the channels to show (default: the first channel, plus any channel that has an applied force). The trace of channel k contains only the conversions of that channel (matched through the sample `address`), drawn as a stair-step held until that channel's next conversion, plus markers at its conversion instants; the existing "ADC hold samples" markers keep showing the ideal value at the same instants so the quantisation error is visible. A channel with no conversion in the run shows nothing and is reported in the status bar. The ADC-Out of the ticked channels (and their codes) also go into Export data as extra columns, and a new "Export samples" CSV lists `t, label, address, v_in, noise_mv, code, v_out`.
- The adapter's `samples` entries get an optional numeric `address` (7953 currently labels `Ch<k>`, ADC124 `addr <k>`; keep the labels, add `address`), needed by B5 for per-sensor series.
- Tests: known input -> expected code and voltage for 8 / 10 / 12 / 16 bit; clipping; rounding at half-LSB; derived node appears in the tree and pulls its source node into `.save`; replot without re-running.

## B3. White noise parameter (Simulation tab)
**Requirement.** A new Simulation-tab parameter adds random white noise, in millivolts, to the ADC input.
- Config `simulation.adc_noise_mV` (float, default 0 = off; a checkbox "Add white noise" plus the value is also fine if the form supports it) and `simulation.noise_seed` (int, default 1; a "random" choice is optional) so runs are repeatable and comparable against a held reference. Manifest group "ADC output" in the Simulation tab.
- Meaning (confirmed): the value is the RMS (standard deviation) of independent Gaussian noise, in mV, added to the ADC input value at every conversion, before quantisation: `v_out = quant(v_in + N(0, sigma))`. Sampling an ideal white source at the conversion instants gives independent samples, so this is white by construction. Say so in the tooltip; mention that it is applied at the conversion instants, not to the continuous waveform.
- Display: the ADC-Out nodes (B2) include the noise; the ideal markers do not. Optionally show the noisy input as markers ("ADC input + noise") so noise and quantisation can be told apart.
- An in-circuit noise source would also let the buffer and the sampling network see the noise, but at the 5 ns solver step it needs millions of PWL points and QSPICE support has not been checked; leave it out of this plan and list it as a possible follow-up.
- Tests: sigma = 0 gives exactly the quantised ideal value; same seed gives identical samples; measured standard deviation of many samples within a few percent of the setting; noise does not change the netlist or any saved QSPICE node.

## B4. ADC range depends on VMID
**Requirement.** If VMID is 0 the ADC output range is -Vref .. +Vref; if VMID is a higher value (for example 1.25 V of 2.5 V, or 1.65 V of 3.3 V) the range is 0 .. Vref.
- Rule (confirmed): `v_low = -vref` when `vmid_v == 0`, else `v_low = 0`; `v_high = vref`. The bipolar range spans 2*Vref, so one LSB is `2*Vref / 2**bits`.
- Implement it in the shared ADC-Out conversion (B2) and show the active range and the LSB in the Derived values box and in the ADC-Out tooltip.
- Circuit consequence to handle explicitly: the models currently clamp signals to 0 .. VDD (OPA365 behavioural rails, mux supply). With `vmid_v = 0` the sensor swings below ground. Confirmed approach: in that mode the behavioural op-amp (and mux) rails are made symmetric, `-vref .. +vref`, with a warning banner "bipolar analog supply assumed (real ADS7953 / ADC124S101 inputs cannot go below 0 V)". Add a manifest/config flag so the models can opt in; if a model cannot, the simulator shows the warning and clips.
- The existing sensor-swing warnings in the adapters (`VMID + v_open > VREF`, release swing below 0 V) must use the new range, and the "initial sensor node" default should follow VMID.
- Tests: ranges and LSB for vmid 0 and > 0; values below 0 are clipped in unipolar mode and kept in bipolar mode; netlist rails change only when `vmid_v == 0`; defaults unchanged.

## B5. Force calculator tab
**Requirement.** A new tab, "Force", with all parameters needed to extract the force (or the change in force dF) from the measured voltage, and with the formulas shown.
- **Parameters** (generic list, each with a "use component value" default): sensor `d33` [pC/N], sensor capacitance [pF], optional extra node capacitance [pF] (default 0; the capacitance the node adds in parallel to the sensor), front-end gain (default 1), reference for the first sample (VMID / first sample), voltage source (ADC-Out quantised+noisy / ideal ADC input), sensors to extract (the chosen channels, same selection as ADC-Out in B2; default all channels that have samples). By default the d33 (with `force_gain`) and capacitance come from the component settings of each sensor (resolved with the B1 override); the user can overwrite any of them for the calculation only, to model using a value that is not the exact component value. An overwritten value is highlighted like other changed parameters; each field has a reset to "follow components" and shows the inherited value as a hint. These force-calculation settings are saved with Save / Load settings and do not change the netlist (so changing them replots, it never re-runs QSPICE).
- Models provide the per-sensor defaults through a new optional adapter function `sensor_info(cfg) -> {address: {"d33_C_per_N": ..., "cp_F": ..., "cextra_F": ...}}` (reuse `sensor_params`); the manifest declares `"force_calc": {"enabled": true}` for models that support it. Models without it hide the tab.
- **Formulas shown on the tab** (a read-only panel, with the live numbers substituted):
  - open-circuit sensor voltage: `V = d33 * F / C`, with `C = C_sensor + C_extra`;
  - change in force between two consecutive conversions of the same sensor: `dF[k] = (V[k] - V[k-1]) * C / (d33 * G)`, `V[0-1]` = VMID or the first sample according to the reference setting;
  - total force: `F[k] = sum(dF[0..k])` (discrete integration of dF), starting at 0;
  - sensitivity `S = d33 / C` [V/N] and the force per LSB `dF_LSB = lsb * C / (d33 * G)`, so the quantisation resolution in newtons is visible.
  The text states plainly that this is the ideal charge model: it ignores the charge sharing with the mux node, leakage and bias-resistor decay, so `F` drifts and the result differs from the applied force when the real circuit deviates; that is the point of the comparison (B6).
- Output table below the formulas: per sensor the min/max of dF and F and the final error against the applied force, plus the per-sample table (`t, address, V, dF, F`) exportable as CSV.
- Tests: with ideal inputs (no noise, tiny LSB) dF and F match a hand-computed result; overriding d33 or C scales the result exactly; changing force-calculator parameters replots without a run; settings round-trip; the tab is hidden for a model without `force_calc`.

## B6. Visualization: show dF, F and Fcal / Fin, with optional log scale
**Requirement.** In the Visualization tab the user can choose to display the calculated dF, the total calculated force F (the integration of dF), and the ratio of the calculated force to the input force, Fcal / Fin. These values can also be shown in log scale.
- Derived nodes per chosen channel (same channel selection as B2 / B5): `dF ch<k>`, `F ch<k>` (= Fcal) in a plot group "Calculated force [N]", and `Fcal/Fin ch<k>` in a plot group "Fcal / Fin [ratio]". The applied (input) force `f<k>` stays selectable in the "Applied force" group; a checkbox "overlay applied force" draws it dashed on the Calculated-force panel for direct comparison. All derived nodes are plotted at the conversion instants (stair or points, as for ADC-Out) and take part in Save image, Export data, the reference overlay and the time window like any other trace.
- **Fin and the ratio:** `Fin[k]` = the applied force of that channel (`f<k>` node) interpolated at the conversion instant of sample k (the instant the ADC held the value; use the sample time `t` from the adapter). `Fcal/Fin[k] = F[k] / Fin[k]`. Where `|Fin|` is below a threshold the ratio is undefined and is left out (NaN, no line) instead of exploding: setting "Minimum |Fin| for the ratio" in the Force tab, default **[assumption]** 1 % of the largest `|Fin|` of that channel in the run, editable in newtons (an exact zero is always masked, since it cannot be divided by). The ratio is 1 for a perfect extraction; below 1 means under-estimated force (for example charge sharing or decay), above 1 over-estimated.
- **Log scale:** each of these panels (and, generically, every plot group) gets a "Log scale (Y)" checkbox in the Visualization tab, stored in the display settings and saved with Save / Load settings. Implementation in the plot panel with pyqtgraph's log mode on the Y axis of that panel. Because forces and dF are bipolar, the log view plots the **magnitude** `|y|` and omits zeros; the axis label then reads "|value| (log)" and a hint explains it; the ratio is normally positive, so for it the log scale is a direct view (the reference line at 1 is drawn). Min/max decimation, zoom and the reference overlay must keep working in log mode, and the ratio panel gets a horizontal marker at 1.
- Selecting these nodes pulls the needed source nodes (sample node, force node) into the run; if the last run did not save them, the status bar says "press Run to include them" exactly like today.
- Tests: ticking `dF` / `F` / `Fcal/Fin` for a channel shows the traces; `F` equals the cumulative sum of `dF`; the ratio equals `F / Fin` at the conversion instants and is NaN below the threshold; the log checkbox switches the Y axis to log mode and plots magnitudes without errors on zeros and negatives; the setting round-trips through Save / Load settings; unticking removes the traces; image export and CSV export contain them.

## B7. Park mode: park on VMID or stay on the last channel (TestBoard_ADC124)
**Requirement (user, 2026-10-26).** The System tab gets a "Park on VMID" toggle. On = the behaviour of today, unchanged. Off = during the park time the mux is **not** switched to VMID: the last sampled channel simply stays connected for the park time. The park time field is renamed from "VMID park time" to "Park time". With one mux, one channel and the toggle off, the model samples the same channel again and again while that channel stays connected the whole time: the mux never switches, so there is no settle wait, no break-before-make gap, no charge injection, no charge redistribution from re-connecting and no other switching effect after the first connection.
- **Config and manifest.** New key `timing.park_on_vmid` (bool, default `true`) in `TestBoard_ADC124/config.json`, shown in the System tab (group "Scan") next to "VMID visit after every sensor". The key `timing.t_vmid_park_us` keeps its name (saved settings, scenarios, `--sweep timing.t_vmid_park_us=...` and the reports use it); only its label and tooltip change to "Park time". A saved settings file without the new key gets the default (`true`). The 7953 model is not changed by this item (it has no park time; its VMID handling is a separate setting).
- **Schedule with the toggle on.** Nothing changes: same slots, same netlist text, same traces (the regression test from Part A keeps passing, including the periodic baselines).
- **Schedule with the toggle off ("park on the last channel").**
  - There is no VMID visit at all. `timing.vmid_visit_after_each` and `timing.t_vmid_settle_us` are ignored (the tooltips and the Derived values say so); the mux is on VMID only before the first address command, as today, and **not** in the tail after the last cycle (the last channel stays connected there too).
  - One sweep = every address of `scan_order` in turn, each connected for `settle + n_mux * repeat` ADC words (as today). After the **last** address of the sweep the same channel stays connected for the park time, then the next sweep starts. The park time is added to the last address' connection (one longer connected slot), not a separate slot.
  - **No-switch rule [assumption, from the firmware: `muxSelect(ch)` returns immediately when the channel is already selected, no address write and no settle delay; see the mux-timing verification notes]:** a visit to the address that is already connected needs no mux command and no `t_sensor_settle_us`; it costs only its `n_mux * repeat` ADC words. The first connection of the run (from the initial VMID park) always pays the settle. With distinct addresses (several channels) every visit is a real switch, so the numbers differ from the toggle-on case only by the missing VMID visit and the park position. With a single channel the cycle is `n_mux * repeat * word + park`, the sample times are uniform, and the control signal of that channel is switched on once and never off.
  - The sample instant of a visit is `command + lead + (repeat - 1) * word + acquisition`, with `lead = settle` for a real switch and `0` for a no-switch visit.
  - `timing.sampling_rate_hz` still works: the park time is derived so that the per-sensor revisit period is `1 / rate` (using the cycle of that mode); an error is raised when the rate is too high, naming the maximum rate.
- **Control signals.** Non-periodic runs already merge consecutive slots of the same address, so a single channel gets one enable pulse. Periodic runs (`>= simulation.periodic_min_cycles`) get a single step (no period) for a one-channel scan; for several channels the last channel's pulse simply ends when the next sweep starts. The sample breakpoints use the sample-to-sample period of the mode.
- **Derived values (System tab).** Show the park mode ("on VMID" / "on the last channel"), "Park time used", the scan cycle, the rate per sensor, the number of mux switches per cycle (0 for a single channel) and a line stating that the VMID settle and VMID-visit settings are ignored in this mode.
- **Not changed.** The analog model (TMUX1308A channel cells, OPA365, parasitics), the ADC-Out / noise / force features (they use the adapter samples, whose `address` and `t` stay valid) and the `.save` list.
- **Tests.** Toggle on: schedule and netlist identical to today (existing tests plus the pinned netlist hashes). Toggle off: no VMID slot (except the initial park), the cycle length formula for 1 and several channels, the no-switch rule (single channel: second and later visits have no settle, the first has), the sampling-rate park derivation and its error, the enable waveform of a single channel has exactly one on-edge and no off-edge before the end (non-periodic and periodic), samples are uniformly spaced, the tail keeps the last channel connected, the Derived values text, the System-tab checkbox and label in a headless GUI test, a real-QSPICE run (skipped without QSPICE) where a single connected channel shows no mux enable edge after the first and the quantity of interest (the charge-injection spike on `ain`) is absent after the first conversion, while the toggle-on run has it at every visit.
- Documentation: `TestBoard_ADC124/README.md` (timing section and the parameter table), the Simulator README (assumptions), `TestBoard_ADC124` tooltips.

## B8. Force calculation with leakage and charge-sharing compensation
**Requirement (user, 2026-10-26).** `dF[k] = (V[k] - V[k-1]) * C / (d33 * G)` takes the voltage difference as the charge the PZT generated. The sensor node also loses charge through the bias resistor and the other leakage paths, while it is connected to the mux and while it floats, so the voltage decays exponentially (R * C) during the time between two conversions. The force must be computed from the **charge the PZT actually generated** (from the system parameters and the timing), not from the charge that is visible in the ADC output.
- **Physical model (generic, per sensor).** Node voltage V is the voltage at the mux/buffer node; it is observed at every conversion. Between two conversions of one sensor the sensor passes through up to three phases (connected after the first conversion, floating, connected before the second conversion), each a first-order circuit `C dV/dt = -(V - Vrest)/R - I + q(t)` (q = piezo current):
  - **connected** (mux node and sensor joined): capacitance `Ct = Cs + Cn`, leak resistance `R_conn` (bias resistor) to `V_conn` (= VMID), constant current `I_conn`;
  - **floating**: capacitance `Cs`, leak resistance `R_float` (insulation) to `V_float` (0 V), constant current `I_float` (mux off-leakage / pin leakage; positive = discharging the node);
  - at every **re-connection** the sensor charge is shared with the mux node, which was parked on VMID: `V = rho * V_sensor + (1 - rho) * V_conn`, `rho = Cs / (Cs + Cn)`. This charge-sharing loss is not a leak in time but removes charge at every visit, so it is part of the same correction. (`Cs` = sensor capacitance + sensor-side parasitics, `Cn` = capacitance of the shared mux node.)
  Solution of one phase of length d: `V(d) = V_inf + (V0 - V_inf) * exp(-d/(R C))`, `V_inf = Vrest - I R`; with no resistor (`R = inf`) the node drifts linearly, `V(d) = V0 - I d / C`.
- **Extraction.** For consecutive conversions k-1 -> k of one sensor, V_pred[k] is the voltage the node would show at conversion k if the sensor generated **no** new charge (V[k-1] propagated through the phases above). The difference `V[k] - V_pred[k]` is caused by the new charge `dQ[k]`. The new charge arrives during the interval (assumed uniformly in time, **[assumption]**) and is attenuated by the decay and the charge sharing that follow its arrival; summing the three phases gives the gain `h[k] = dV[k]/dQ[k]` (in V/C), so `dQ[k] = (V[k] - V_pred[k]) / h[k]`, `dF[k] = dQ[k] / d33` (the front-end gain G divides the voltage change around VMID as before), `F = cumsum(dF)`. With no leakage and no node capacitance this reduces exactly to the ideal formula, which stays available (checkbox off). First conversion of a sensor: the node starts at the reference (VMID), `dQ[0] = Ct * (V[0] - V_conn) / a3` (with the reference "first sample", dF[0] = 0 as before).
- **Timing needed.** Each conversion in the adapter's `samples` list gets optional `t_on` (the instant the sensor was connected, break-before-make delays included), `t_off` (the instant it was released again, or the end of the run) and `node_reset` (the mux node was parked on VMID before this connection). A conversion whose window contains the previous conversion of the same sensor (a sensor that stays connected, see B7) is a single connected phase and has no re-connection. Samples without these keys, or a model without `sensor_info()["leak"]`, are extracted with the ideal formula (and the Force tab says so).
- **Model parameters (`sensor_info(cfg)[address]["leak"]`).** `c_side_F`, `c_node_F`, `r_conn_ohm`, `v_conn_V`, `i_conn_A`, `r_float_ohm`, `v_float_V`, `i_float_A`. ## B9. Force tab: remove the front-end gain G, full explanation of the charge model
**Requirement (user, 2026-10-27).** The boards have no gain stage, only a unity-gain buffer, so the front-end gain `G` is an unnecessary parameter. It is removed from the force calculation (settings, Force tab, formulas, README, tests). The explanation of the charge model in the Force tab is expanded.
- **Removal.** `FORCE_DEFAULTS["gain"]`, `SensorParams.gain`, the field "Front-end gain G" and every `/ G` disappear: `dF[k] = (V[k] - V[k-1]) * C / d33`, `dF_LSB = lsb * C / d33`, and `vn = v` in the compensated extraction. A saved settings file that still has `force.gain` loads without error (the key is ignored). The sensor component's `force_gain` (scales the applied force in the netlist) is a different thing and stays.
- **Formula panel with leakage compensation (default).** Sections, each with the live numbers of the shown channel:
  1. *What the ADC sees:* `V = Q_node / C`; the open-circuit sensor voltage `V = d33 F / C`; the charge the PZT generates `dQ = d33 dF`.
  2. *Breakdown of the node* (a table): charge from the PZT (`q`), leakage through the bias resistor (`(V - V_conn)/R_conn`, connected), leakage from the mux / op-amp pins (`I_conn` connected, `I_float` floating), insulation leakage (`(V - V_float)/R_float`, floating), charge sharing with the mux node at every connection (`rho = Cs / Ct`), each with its model value (R, I, C, tau).
  3. *Full equation:* `C dV/dt = q - (V - Vrest)/R - I` per phase (a current balance: `q = d33 dF/dt` is the PZT's charge **rate** in amperes, not a charge; constant between two conversions, so `q = dQ[k] / T` and `dQ[k] = q T`), and its solution `V(d) = V_inf + (V0 - V_inf) e^(-d/RC)`, `V_inf = Vrest - I R`, the unit-rate response `g(d) = R (1 - e^(-d/RC))`.
  4. *Mux switching* (connected -> floating -> re-connection -> connected): the four steps, `V_pred[k]`, `h[k] = g1 a2 rho a3 + g2 rho a3 + g3`, `dQ[k] = T (V[k] - V_pred[k]) / h[k]`.
  5. *Constant connection* (the sensor stays connected, no switching): `V_pred[k] = V_inf + (V[k-1] - V_inf) a`, `h = R (1 - a)`, `a = e^(-T/tau)`, `dQ[k] = T (V[k] - V_pred[k]) / h`, and its small-T limit `dQ ~ Ct dV + ((V[k-1] - V_conn)/R_conn + I_conn) T`.
  6. *Result:* `dF = dQ / d33`, `F = sum dF`, the first-sample rule, the reduction to the ideal formula and the stated limits.
  The numbers shown: Cs, Cn, Ct, rho, R_conn, tau_conn, R_float, tau_float, I_conn, I_float, T of the channel (median interval) and which equation (switching or constant connection) the channel uses (from the node_reset / window data: conversions per case are counted).
- **Ideal charge model panel** (checkbox off): the same layout with the short formulas only, naming the ignored effects.
- **Leakage override fields (2026-10-27).** The Force tab gets "Leakage current, sensor connected" (`force.i_conn_nA`, empty = follow the model, 0 = no connected leakage) next to "Leakage current, sensor floating" (`force.i_float_nA`). `I_float` acts only in the released phase, so it has no effect on a sensor that stays connected (one channel parked on itself); the tooltips and the formula panel say so. `I_conn` acts in every connected phase.
- **Tests.** No `gain` in `FORCE_DEFAULTS` / the tab fields; old settings with `gain` load; `dF` of the ideal model without G; the panel text contains the sections and the live numbers; the constant-connection case is stated when the windows hold the previous conversion, the switching case otherwise.
